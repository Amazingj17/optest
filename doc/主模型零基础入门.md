# 从零理解 CPN-HRL-DAG：主模型的设计与工作方式

> 面向读者：不了解 DAG、神经网络或强化学习，也可以从头阅读。
> 说明依据：当前仓库的代码与配置，不是对原始论文的逐条复现说明。
> 主体：LSTM + GAT 分层强化学习模型，以及可选的 HEFT-safe 安全搜索层。Graph PPO、Tier MAPPO、DAG-pair 属于其他对比或扩展路线。

## 1. 一句话：这个项目做什么？

**给一批有先后依赖的计算任务安排执行顺序和执行机器，让整批任务尽早完成。**

可以把它想成一家厨房：有些工序可以同时做，有些必须等前一道工序；厨师速度和能力不同；交接半成品需要时间。因此，不仅要决定“接下来安排什么”，还要决定“交给谁”。

| 厨房里的概念 | 项目里的概念 |
| --- | --- |
| 一道工序 | 计算任务 task |
| 工序的先后关系 | 任务依赖 |
| 厨师或工作台 | 计算节点 compute node |
| 厨师的速度和专长 | 计算速度、设备能力 |
| 交接半成品 | 跨节点数据通信 |
| 工序安排表 | 调度结果 schedule |
| 最后一道工序完成的时刻 | 总完工时间 makespan |

这里的主模型是**调度决策模型**，不是聊天大模型，也不负责实际执行任务中的计算业务。

## 2. 先弄懂四个基础概念

### 2.1 DAG：不会绕回来的任务依赖图

DAG 的中文是“有向无环图”。看一个例子：

```text
      ┌── B ──┐
A ────┤       ├── D
      └── C ──┘
```

A 的结果准备好后，B、C 才能执行；B、C 之间没有直接依赖，可以在不同机器上并行执行；D 必须等 B、C 的结果都到齐。

不允许出现“A 等 B，B 又等 A”的循环。箭头还携带数据量：相邻任务不在同机时，数据传输会增加等待。

### 2.2 云、边、端与异构资源

可以粗略地把“端”理解为终端设备，“边”理解为靠近终端的服务器，“云”理解为远端服务器。

**名称不等于固定的性能排名。** 程序依据场景里的具体速度、设备能力、容量、带宽和时延决策，并不是永远选择云。

“异构”就是机器各不相同：同一个任务在不同机器上可能耗时不同，有的机器甚至无法执行它。

### 2.3 调度：先填写计划，不是按真实时间等待

当前核心环境是**离线列表调度**：已知任务和资源，逐步填写完整执行计划。

必须区分“已安排”和“已执行完”：

- 已安排：已确定在哪台机器、何时开始和结束。
- 已执行完：真实时间已经经过任务结束时刻。

代码里的 ready 表示“所有前驱都已安排，因此可以计算并安排本任务”，**不表示前驱已经在现实中跑完**。真正执行时，开始时间仍要满足数据到达约束。

例如 A 一旦安排好，B、C 就可以进入待选列表，但它们不能在 A 的结果到达前开始执行。

### 2.4 目标：让最后一个任务尽早结束

如果三个任务结束于 5、8、12，那么 makespan 是 12，不是 25。

项目主要比较：

```text
ratio = 当前策略的 makespan / 同一场景下 HEFT 的 makespan
```

1.00 表示一样；0.90 表示总完工时间少了 10%；1.10 表示多了 10%。HEFT 是后面会介绍的参考调度算法。

mean_ratio 是多个场景的比值取平均，不是把各策略所有完工时间分别相加后再相除。越小越好，但还要检查排程是否合法、生成排程用了多久。

## 3. 整个系统如何分工？

```text
原始数据 → 数据适配器 → Scenario（统一的任务与资源描述）
                              ↓
Environment：将当前排程状态整理成数字特征
                              ↓
高层 LSTM：下一步安排哪个任务？
                              ↓
低层 GAT：该任务交给哪台机器？
                              ↓
ScheduleSimulator：计算开始/结束时间，写入时间线
                              ↓
更新状态，重复两层决策，直到安排完所有任务
                              ↓
Evaluator：检查结果并统计指标
```

环境内部调用模拟器，不是两者各算一套时间。数据适配器像翻译员，Scenario 像题目，模型像决策者，模拟器执行排程规则，Evaluator 检查并统计成绩。

**模型选择“任务 + 机器”，模拟器计算“什么时候执行”。模型不直接预测开始时间。**

## 4. 为什么分成高层和低层？

假设有 100 个任务、10 台机器，直接考虑任务—机器配对，就有 1,000 个组合位置，其中不少还不合法。

本项目把一次完整动作拆成：

1. **高层选任务**：从已经可以安排的任务中选一个。
2. **低层选机器**：知道具体任务后，比较它放到各机器上的情况。

这就是“分层强化学习”的分层。不是高层管云、低层管端，也不是高层一次选择一批任务。

好处是分工清晰，低层还能使用针对所选任务计算的候选耗时。代价是两层需要配合；分层本身不保证全局最优。

## 5. 高层 LSTM：下一步安排谁？

### 5.1 输入：每个任务一行数字

环境为每个任务生成 17 个数字。有 N 个任务，就有一张 N × 17 的表，主要包括：

- 工作量、前驱数、后继数、拓扑层级、是否为起点或终点。
- 是否已安排、是否 ready、前驱已安排的数量或归一化比例。
- 在不同节点上的平均、最短、最长执行时间。
- 输入和输出数据量。
- HEFT 优先级及其尺度、整体安排进度。

环境还为每台资源提供 5 个数字：速度、时间线最晚结束时间、已分配任务数、CPU 容量、内存容量。

启用归一化后，许多时间特征除以本场景 HEFT 的完工时间，相当于将秒数换成参考时间的比例，减少不同任务规模的数值差异。

### 5.2 网络：读取任务列表，再给任务打分

LSTM 可以先理解为“按顺序阅读一串描述，结合前面的内容形成表示”的神经网络。

```text
任务的 17 维特征
    ↓ 线性层 + tanh，转换为内部表示
128 维表示（示例配置）
    ↓ LSTM，沿当前任务列表处理
每个任务的上下文表示
    ├── Actor：每个任务一个分数
    └── Critic：汇总任务与资源信息，估计后续回报
```

- **Actor** 是决策分支，回答“选哪个动作”。
- **Critic** 是评价分支，估计后续累计奖励，帮助训练；它不是额外的排程动作，也不是已验证的最终完工时间。

三个重要实现细节：

1. LSTM 处理的是当前 Scenario 的任务列表，不是按真实执行时刻播放任务。
2. 每次决策重新计算，代码没有把 LSTM 隐状态跨调度步持续传递。此前安排主要通过当前观测体现，不能把它描述成持续记住全部历史动作的记忆器。
3. 额外的 5 维资源信息汇总直接进入高层 Critic，不直接拼进高层 Actor；任务特征本身仍含执行时间等资源相关摘要。

### 5.3 Mask：给不合法动作上锁

mask 就是一份“可选/不可选”清单。已安排任务不能再选，前驱尚未全部安排的任务不能选，只有 ready 任务可以被选中。

代码中的 task_mask 与 ready_mask 不同：前者用于任务表示的有效性与汇总，当前环境的真实任务均有效；后者才限制当前动作。模型可以观察未 ready 的任务，但不能选择它们。

## 6. 低层 GAT：交给哪台机器？

### 6.1 为什么使用图网络？

机器之间有网络连接，带宽和时延影响数据传输。GAT 即“图注意力网络”，可以理解为：每台机器形成表示时，会有选择地参考相连机器及连接特征。

**这里 GAT 处理的是资源网络图，不是直接在任务 DAG 上做图消息传递。** 任务依赖通过任务特征、前驱位置和候选耗时参与决策。

### 6.2 输入：针对当前任务比较每台机器

高层选定任务后，环境为每台机器计算 8 个数字：

| 特征 | 含义 |
| --- | --- |
| speed | 机器速度 |
| execution_time | 该任务在此机器上的执行时长 |
| communication_time | 从已安排前驱接收数据的通信时间项之和 |
| dependency_ready_time，DRT | 所有前驱结果最早到齐的时刻 |
| EST | 考虑依赖与空闲时段后的最早开始时刻 |
| EFT | 对应的最早结束时刻 |
| available_at | 当前时间线上最晚结束时刻，前面仍可能有空档 |
| assigned_task_count | 已分配任务数 |

另有当前任务的 17 维特征、资源连接关系，以及连接上的带宽和时延特征。

通信时间之和不等于 DRT：多个前驱的数据到达约束取最晚到达者，不是把所有前驱时间串行累加。

### 6.3 网络如何计算？

```text
节点特征 + 连接关系 + 连接特征
    ↓ 第一层 GAT（示例为 4 个注意力头）
    ↓ 第二层 GAT
每台机器的 64 维表示（示例配置）
    + 当前任务的编码
    + 原始节点特征中的时间量、任务数等信息
    ↓ Actor
每台机器一个分数 → 节点 mask → 选择机器
```

多个注意力头可以理解为从几种角度同时比较资源，本实现对各头输出求平均。低层也有 Critic，利用汇总节点表示和当前任务特征辅助训练。

### 6.4 忙的机器能不能选？

**能。忙碌影响 EST/EFT，不直接禁止选择。** 等一台忙但快的机器，可能比马上用一台空闲但慢的机器更早完成。

节点 mask 检查的是任务与资源的永久可行性，例如设备能力和容量约束。机器忙碌不是永久不可行。

## 7. 模拟器怎样计算具体时间？

### 7.1 执行时间与通信时间

简单速度执行模型使用：

```text
执行时间 = 任务工作量 / 节点速度
```

GrapheonRL 场景默认使用设备相关执行模型，按任务所需设备选择节点对应速度。代码也定义了固定时长模型，但并非所有场景都使用它。

通信模型使用：

```text
同机通信时间 = 0
跨机通信时间 = 数据量 / 两机带宽 + 两机时延
```

这是直接节点对通信模型，不自动寻找多跳路由，也没有模拟共享链路上的带宽争用队列。

### 7.2 等数据，再寻找能放下任务的空档

```text
DRT = 所有前驱“结束时刻 + 传到目标机器的耗时”的最大值
EST = 目标机器上，不早于 DRT 且足够放下整个任务的最早空档起点
EFT = EST + 执行时间
```

这叫**插入式调度**：可以插进已有任务之间的空档，不一定排到最后。

任务一旦开始就连续执行到结束，不暂停再恢复，称为“非抢占”。当前节点时间线要求任务不重叠，不是看到多核 CPU 就自动让同节点多个任务并发运行。

## 8. HEFT 残差：在经验规则上学习修正

### 8.1 HEFT 是什么？

HEFT 是项目的参考启发式，不是训练出来的网络。先记两条规则：

1. 为任务计算 upward rank，粗略表示从该任务往后的依赖链还剩多大的计算与通信负担；优先安排 ready 任务中 rank 高的。
2. 为选中的任务挑选 EFT 最小的可行节点。

它提供一份参考计划，但不证明全局最优。

### 8.2 残差是什么意思？

启用 heuristic_residual 后，可以将打分理解为：

```text
高层分数 = 8 × 归一化 upward rank + 0.5 × tanh(网络输出)
低层分数 = -8 × 归一化 EFT       + 0.5 × tanh(网络输出)
```

8 与 0.5 是示例配置中的值，可调整。tanh 把网络输出压到约 -1～1，所以修正项的幅度不超过约 ±0.5。

直观上就是：**先参考 HEFT，再允许模型做有限调整。** 低层 EFT 前面取负号，是因为结束时间越小越好，而系统挑分数大的候选。

### 8.3 初始模型为什么能复现 HEFT？

残差模式把 Actor 最后一层初始化为零，初始修正项为零。确定性推理包装器还会检测零残差，直接按 HEFT 优先级和精确 EFT 选择，并固定处理同分情况，从而复现 HEFT 排程。

但要区分：

- 训练通常按概率采样，即使初始修正为零也可能探索其他动作。
- 训练后的纯模型仍可能比 HEFT 差，限制修正幅度不是性能保证。
- 基础配置 `configs/cpn_hrl_dag.yaml` 没有开启残差，不能说所有配置默认都是残差模型。

## 9. 一个完整的手算例子

以下仅为教学数字，**不是仓库实验结果，也不代表训练模型一定这样选择**。

依赖关系仍为 A → {B, C} → D，有快机器 F、慢机器 S：

| 任务 | 在 F 上耗时 | 在 S 上耗时 |
| --- | --- | --- |
| A | 2 | 4 |
| B | 3 | 6 |
| C | 2 | 4 |
| D | 1 | 2 |

假设每条依赖跨机器传输耗时为 1，同机为 0。

**第一步：安排 A。** 一开始只有 A ready，假设选 F，得到 A [0, 2]。

**第二步：安排 B。** A 已安排，B、C 都 ready。假设先选 B，并选 F，得到 B [2, 5]。

**第三步：安排 C。** 对比两个位置：

- 放 F：A 的结果在 2 就绪，但 2～5 已安排 B，因此 C 为 [5, 7]。
- 放 S：A 的结果在 2 + 1 = 3 到达，因此 C 为 [3, 7]。

两者 EFT 都为 7。假设选择 S。

**第四步：安排 D。** 假设选 F，B 的结果在 5 可用，C 的结果在 7 + 1 = 8 到达。DRT 为 max(5, 8) = 8，D 执行于 [8, 9]。

```text
F：A [0, 2] → B [2, 5] → 空闲 → D [8, 9]
S：空闲 → C [3, 7]
```

最终 makespan 为 9。程序按 A、B、C、D 填写计划，但 B、C 的实际执行时间重叠。

这个例子说明：**决策顺序不等于真实执行的时间顺序；是否 ready 也不等于现在就能执行。**

## 10. 模型如何学会改进？

### 10.1 PPO：尝试、反馈、小步调整

强化学习不是每一步都给唯一标准答案，而是让模型尝试决策，再根据结果改进。项目用 PPO：

1. 将当前分数转成概率，采样合法动作。
2. 保存观测、动作、动作概率、Critic 估计与奖励。
3. 完成排程，估计各动作比此前预期好还是差。
4. 鼓励表现较好的动作，抑制较差动作。
5. 限制更新幅度，避免策略突然改变太多。

PPO 的裁剪约束针对训练目标中的概率变化，不是把最终 makespan 截断成一个好看的数。

### 10.2 奖励如何计算？

基础奖励是：

```text
本步奖励 = -(当前部分排程 makespan - 上一步部分排程 makespan) / HEFT makespan
```

如果 HEFT 完工时间是 100，本次安排使部分 makespan 从 20 增到 25，奖励就是 -0.05。如果任务填入空档、没有增加最晚结束时间，基础奖励是 0；这不意味着任务没有执行成本。

关闭额外奖励项、从空排程开始时，基础奖励**不折扣地相加**，恰好等于 -最终 makespan / HEFT makespan。提高累计奖励就对应缩短总完工时间。

训练还使用折扣系数 gamma。gamma 小于 1 时，不同时刻的奖励权重不同；示例残差配置两层 gamma 都为 1。通信惩罚、势函数塑形是可选项，该示例中均关闭。

### 10.3 训练分阶段进行

| 阶段 | 谁选任务 | 谁选机器 | 更新谁 |
| --- | --- | --- | --- |
| low_pretrain | HEFT 优先级规则 | 低层网络 | 低层 |
| high_train | 高层网络 | EFT 规则 | 高层 |
| joint | 高层网络 | 低层网络 | 两层分别更新 |

可以理解为先固定一位搭档的行为，让另一位学习，再共同配合。联合阶段两层接收同一次完整动作的环境奖励，但各自有网络、Critic 和优化器。具体阶段是否运行由配置决定。

代码还支持可选的行为克隆初始化，即先模仿示范；它不等于 PPO，也不是所有配置都启用。

### 10.4 一份具体配置

以 `configs/zenodo_heft_safe_fast_2026.yaml` 为例：

| 配置项 | 设置 |
| --- | --- |
| 高层 | 128 维 LSTM，开启残差 |
| 低层 | 64 维、第一层 4 头 GAT，开启残差 |
| 观测归一化 | 开启 |
| 低层预训练 | 0 个 episode |
| 高层训练 | 75 个 episode |
| 联合训练 | 75 个 episode |
| 行为克隆 | 关闭 |
| 验证间隔 | 每 25 个 episode |
| 设备 | 配置为 CUDA |

一个 episode 是对一个场景完成整份排程，不是只安排一个任务。训练次数是计划上限，早停等机制可能提前结束；也不能保证训练这些次数就必然达到某个成绩。

### 10.5 如何挑选和保存模型？

- 训练集像练习题，用来更新参数。
- 验证集像模拟考试，用来选择模型和判断是否继续训练。
- 测试集像最终独立考试，不应用来反复调参。

脚本保存验证表现较好的 best.pt 和最近状态 latest.pt，包含两层网络、优化器、配置等信息。启用代理验证子集时，会先进行小规模筛查，在满足条件时再做完整验证，因此不是每个检查点都有完整验证结果。

## 11. 训练与推理有什么不同？

| 方面 | 训练 | 常规确定性推理 |
| --- | --- | --- |
| 动作选择 | 按概率采样，允许探索 | 选合法候选中分数最高的 |
| 参数 | 通过 PPO 更新 | 不更新 |
| Critic | 辅助计算学习目标 | 不负责选择动作 |
| 奖励 | 用于学习 | 可被环境计算，但不更新网络 |
| 主要产物 | 轨迹、损失、检查点 | 排程及指标 |

推理仍需要模拟器计算候选时间，残差和归一化还使用 HEFT 信息。因此它不是完全不需要时间模型或启发式的黑箱。

## 12. 安全搜索层：什么情况下保证不差于 HEFT？

### 12.1 先区分运行模式

| 策略名 | 做什么 | 需要检查点？ | 同一模拟器下不差于 HEFT？ |
| --- | --- | --- | --- |
| heft | 参考 HEFT | 否 | 就是参考本身 |
| hrl | 纯两层学习策略 | 是 | 不保证 |
| portfolio | HEFT 与一组候选排程择优 | 否 | 是 |
| search | 使用配置中的增强搜索 | 否 | 是 |
| hrl_safe | portfolio 加学习策略候选 | 是 | 是 |
| hrl_search_safe | 增强搜索加学习策略候选 | 是 | 是 |

增强功能由配置决定，仅改为 search 不会自动打开全部搜索机制。

### 12.2 保证来自保留 HEFT 候选，不是网络永远正确

```text
生成标准 HEFT 完整排程，并始终保留
    + 其他启发式或扰动候选
    + 可选学习策略候选
    + 配置启用的局部搜索
    ↓
用相同模拟规则计算各完整候选的 makespan
    ↓
选择最小者，再通过公共选任务/选节点接口回放
```

如果 HEFT 是 100，模型是 105，搜索候选是 95，就选 95。如果其他候选都更差，仍可选 100。

因此在合法场景、相同模拟语义下，安全组合的 makespan 不大于候选中的 HEFT makespan。**这不包括生成多个候选的计算耗时，也不是现实部署性能承诺。** 排程质量和规划耗时应分别报告。

### 12.3 增强搜索在做什么？

可以先将它们理解为增加备选方案：换任务优先级或未来代价估计方式（如 PEFT、CPOP），尝试其他任务或节点，调整拖慢总体完工的关键任务链，同时保留若干较好候选继续搜索，并用缓存减少重复计算。

这些是搜索器的能力，不是 LSTM/GAT 内部自动包含的功能。安全组合的提升不能全部算成神经网络独立取得的提升。

## 13. 输出与能力边界

输出是一份完整计划：任务对应节点、开始和结束时间、决策顺序，以及完工时间和通信/计算时间统计。

它不是自动将真实业务发送到云服务器执行的完整生产平台。核心模拟器依据给定时间模型生成排程，不能据此认为现实中的故障、耗时波动、链路争用等问题均已解决。

还要区分三件事：

- **合法**：不违反任务依赖、资源可行性与节点时间线等规则。
- **较好**：指标优于某个参考策略。
- **最优**：所有合法排程中最好；主模型和安全搜索均不普遍保证这一点。

## 15. 最后只记住六句话

1. **目标**：把有依赖的任务分配给不同机器，让最后一个任务尽早完成。
2. **高层**：LSTM 从 ready 任务中选一个。
3. **低层**：GAT 结合资源连接与任务相关时间特征，为它选择机器。
4. **规则**：模拟器负责依赖、传输、空档及具体执行时间。
5. **学习**：PPO 根据反馈训练；残差模式在 HEFT 建议上做有限修正。
6. **安全组合**：比较 HEFT、学习与搜索的完整排程，而不是相信模型建议必然最优。

把它想成“有经验规则辅助的两层排程员，加上统一的排程计算器和可选的多方案比较器”，就抓住了主模型设计的核心。
