## 2. 训练阶段语义

阶段只声明三件事：**谁采样、谁用固定规则、谁能被更新**。

| 阶段名 | 高层动作 | 低层动作 | 可更新模块 |
| --- | --- | --- | --- |
| `high_only_eft` | PPO 采样 | 固定最小 EFT | 仅 high |
| `low_only_frozen_high` | 冻结 checkpoint 策略（默认确定性，可显式配置随机采样） | PPO 采样 | 仅 low |
| `joint` | PPO 采样 | PPO 采样 | high + low |
| `low_pretrain`（历史语义） | 确定性（按 rank 选任务） | PPO 采样 | 仅 low |

要点：

- **旧配置语义不变。** `high_train_episodes` 与显式阶段 `high_only_eft` 完全等价
  （`decision_policy('high_train') is decision_policy('high_only_eft')`，有测试覆盖）；
  `low_pretrain_episodes` / `joint_train_episodes` 同样保持原义。
- **`DecisionPolicy` 会拒绝自相矛盾的组合**，例如「joint 更新但某一层用固定规则」，
  或「不更新却仍用自己的策略采样」。
- 没有第二套 trainer：`hierarchical_trainer._episode` 接收阶段对象，行为差异全部来自阶段声明。

### 冻结不只是关掉 `optimizer.step`

`high_only_eft` 冻结低层、`low_only_frozen_high` 冻结高层时，被冻结的一侧：

1. 切到 `eval()` 并**在整个 episode 内保持不变**；
2. 全部参数 `requires_grad=False`（不会有意外梯度）；
3. 不创建 rollout 更新、不调用 `optimizer.step()`、**不推进 lr scheduler**；
4. 诊断里该层的 `loss / approx_kl / policy_loss / value_loss / entropy / clip_fraction /
   explained_variance / learning_rate` 全部写 `null`，并置 `diag_<level>_module_frozen = true`，
   **不会伪装成测得的 0**。
5. 若误调 `PPOAgent.update`，会直接 `RuntimeError`，而不是静默跳过。

可更新的另一侧照常更新，`budget.json` 与 `summary.json` 记录**实际**更新次数。

## 3. 新增配置字段与默认值

| 字段 | 默认值 | 含义 |
| --- | --- | --- |
| `training.phases` | 缺省 | 显式阶段表，元素为 `{name, episodes, frozen_high_mode?}`。缺省时按旧的三个 episode 计数推导 |
| `training.phases[].frozen_high_mode` | `deterministic` | 仅对 `low_only_frozen_high` 有意义：`stochastic`（冻结高层仍采样，但不保证与联合训练相同状态分布）或 `deterministic`（冻结高层取贪心） |

| `fork.scheduler_restore` | `fresh` | 分叉实验的 scheduler 处理方式：`fresh` 按本实验自身 step 预算重建；`restore` 才继承 checkpoint 的 scheduler 状态。非法值直接报错 |

旧配置无需任何改动即可继续运行。

## 4. 诊断字段

### 4.1 采集约束

- **不额外采样、不改动随机数状态。** 高层与低层的分布统计都来自**已经存在的那一次前向**：
  `PPOAgent.act_with_stats` 在采样的同一个 `Categorical` 上取 `probs / entropy / argmax`，
  既不重新前向也不重新采样。有测试比对「关闭诊断 / 开启诊断」两种情况下
  episode 结果与之后的 NumPy、Torch 随机数序列完全一致。
- **所有比较基于同一个当前状态。** 高层「贪心动作」是同一次前向 logits 的 argmax；
  低层 EFT 比较用的是环境已经算好的 `heft_makespan` 与 float64 `heft_features`。
- **区分单一合法动作与多合法动作。**
- **区分 EFT 并列最优与真正次优：** `low_min_eft_selected_decisions`（落在并列最小集合内，含非最小下标的并列）
  与 `low_suboptimal_decisions`（严格更差）分开计数；`low_deviation_rate_from_min_eft` 比较最小 EFT 下标规则，`low_deviation_rate_from_greedy` 则比较网络分布 argmax。
- 诊断关闭时完全不写 `diag_*` 字段；冻结模块的指标为 `null`。

### 4.2 逐 episode 字段（`training_diagnostics.jsonl` / `.csv`）

标识：`episode`、`global_step`、`epoch`、`phase`、`scenario_id`、`num_tasks`、`transitions`、`coverage`。

回报与 makespan：

- `decisions`、`reward`、`final_makespan`、`heft_makespan`、`makespan_ratio`；
- `diag_makespan_over_heft`（= `makespan_ratio`，即 episode 的 makespan/HEFT）；
- `diag_reward_equals_negative_makespan_ratio`（验证 `gamma=1`、无附加奖励时回报恰为负的 makespan ratio；
  未来若改动奖励，这一列会直接变 `false` 而不是让目标悄悄失效）。

高层动作：

- `diag_high_entropy_active`、`diag_high_expected_log_probability_active`、`diag_high_chosen_probability_active`；
- `diag_high_deviation_rate_from_greedy`（相对同一次前向 argmax 的偏离率）；
- `diag_high_deviation_rate_from_heft_rank`（相对当前 ready 集合 HEFT 优先任务的偏离率）；
- `diag_high_rank_tie_decisions`、`diag_high_rank_missing_decisions`。

低层动作：

- `diag_low_entropy_active`、`diag_low_choice_probability_mean_active`；
- `diag_low_deviation_rate_from_min_eft`、`diag_low_deviation_rate_from_greedy`、
  `diag_low_suboptimal_rate_active`；
- `diag_low_min_eft_tie_decisions`、`diag_low_min_eft_selected_decisions`、`diag_low_suboptimal_decisions`；
- `diag_low_selected_eft_gap_mean_active` / `_p95_active` / `_max_active`
  （选中节点 EFT 与最小可行 EFT 的精确差值，与 HEFT 同一量纲与精度）；
- `diag_low_eft_field_missing_decisions`（缺精确 EFT 时明确排除，不猜）。

PPO 与优化器（每层一套 `diag_high_*` / `diag_low_*`）：

- `loss`、`policy_loss`、`value_loss`、`entropy`、`approx_kl`、`clip_fraction`、
  `grad_norm`、`update_batches`、`train_ratio_mean`、`train_ratio_max`、`learning_rate`；
- `explained_variance` 与 `explained_variance_defined`、`return_variance`：
  当回报方差为 0（例如 `gamma=1` 且回报恒定）时 explained variance 无定义，
  此时 `explained_variance_defined=false`，数值不当作「critic 完全无效」的证据；
- `module_frozen`。

`train_log.csv` 另外保留兼容列并新增：`phase_semantics`、`trainable_modules`、
`high_optimizer_updates`、`low_optimizer_updates`、`decisions`、`final_makespan`、`heft_makespan`、`makespan_ratio`。
旧列（`step` 语义、`high_loss`、`low_loss`、`high_kl`、`low_kl`、`high_lr`、`low_lr`）继续存在。
新日志的 episode 索引用 `episode`，全局计数用 `global_step`（分叉实验里它延续来源 checkpoint 的计数）。

## 5. 只读诊断入口

```
python scripts/diagnose_hrl_execution.py \
  --checkpoint <ckpt.pt> \
  --output <new dir> \
  --modes greedy repeat_sample fixed_low_eft \
  --repeats 3 --per-group 1 --seed 2026 --device cpu
```

- 三种执行模式：`greedy`（高层确定性 + 低层确定性）、`repeat_sample`（两层都采样，重复 K 次）、
  `fixed_low_eft`（高层采样 + 低层固定最小 EFT）。
- **样例固定且预先声明**：从 training split 中按 `(任务规模, 资源类型)` 分组，用固定 seed 抽
  `per-group` 个，选点只由 seed 和 scenario_id 排序决定，不能事后挑有利样例。
- 输出：`diagnostic_plan.json`、`diagnostic_per_run.jsonl`、`diagnostic_summary.json`；
  每个模型都会写入 `split: train_diagnostic`、`formal_validation: false`、
  `formal_validation_scenarios: 108`，明确它**不能替代正式 108 场景 validation**。
- 结果目录与 checkpoint 目录分离，脚本拒绝覆盖已有目录。

### 已实测结果（`outputs/stage1_diagnostic_seed2026_checkpoint864/`）

对正式主模型 `outputs/gpu/outputs/all_models_seed2026/training/residual_hrl/best.pt`
（`global_step=864`，即第一轮结束的选中 checkpoint），6 个固定训练来源样例
（50/100/300 × 同构/异构），`repeats=3`，CPU：

| 模式 | mean ratio | std | min | max | 三次重复均值 |
| --- | ---: | ---: | ---: | ---: | --- |
| `greedy` | 1.001698 | 0.004432 | 0.998857 | 1.011567 | 1.001698（确定性，重复相同） |
| `repeat_sample` | 1.189064 | 0.181956 | 1.036660 | 1.584087 | 1.146529 / 1.259700 / 1.160964 |
| `fixed_low_eft` | 1.022211 | 0.026261 | 0.998682 | 1.098519 | 1.040749 / 1.017718 / 1.008167 |

由此得到两个**实测差值**（同一批样例、同一 checkpoint）：

- 高低层共同采样相对共同贪心的模式差：`repeat_sample - greedy = +0.187366`；
- 采样高层条件下两种低层规则的模式差：`repeat_sample - fixed_low_eft = +0.166853`。

> 解读边界：这是 6 个训练来源样例、单次运行的诊断，不是 108 场景正式验证，也不是统计显著结论。
> 它说明低层执行方式值得优先诊断，但不能推断训练退化原因；不同模式会访问不同状态。
> 要下结论必须用 108 场景（同一 HEFT 分母）和更多样例复现。不得把这组数字与 RESULTS.md 的
> 0.999531 并列成正式成绩。

## 6. 两个定位实验

### 6.1 生成配置

```
python scripts/prepare_stage1_forks.py \
  --output outputs/stage1_forks_seed2026 \
  --output-root <训练机上两个分支的输出根目录> \
  --source-checkpoint outputs/gpu/outputs/all_models_seed2026/training/residual_hrl/best.pt \
  --episodes 1728 --coverage-epochs 2 --diagnostics
```

`--output-root` 只在「生成配置的机器与训练机器路径不同」时才需要（例如本机生成、Linux 训练）。
生成后在训练机上跑启动前预检（6 项检查 + 单 episode probe，只打印命令、不启动训练）：

```
python scripts/preflight_stage1_run.py \
  --config outputs/stage1_forks_seed2026/configs/low_only_frozen_high.yaml \
  --fork-from outputs/gpu/outputs/all_models_seed2026/training/residual_hrl/best.pt \
  --report outputs/stage1_forks_seed2026/preflight_low_only_frozen_high.json
```

来源 checkpoint 的选择：正式主模型第一轮（high 层覆盖轮）结束时的 checkpoint 是
`global_step=864` 的 **`best.pt`**，不是 `latest.pt`。两者 `best_validation_ratio` 都是 `0.9995307`，
只能靠步数或权重区分：

| 文件 | global_step | high actor | low actor 输出层 |
| --- | ---: | --- | --- |
| `residual_hrl/best.pt` | 864 | 已训练（128 个非零权重） | **仍然全零**（低层从未训练） |
| `residual_hrl/latest.pt` | 2592 | 已训练 | 已训练（joint 阶段更新过） |

从 `latest.pt` 分叉会得到已联合训练的模型，不再是「第一轮之后的分叉」，所以必须用 `best.pt`。
`fork_plan.json` 记录来源 sha256（`best.pt`：`db0aef70a80943d5…`），可随时核对。

### 6.2 运行命令

分支 A（继续 `high_only_eft`）：

```
python scripts/train_main_comparison.py \
  --config outputs/stage1_forks_seed2026/configs/high_only_eft.yaml \
  --fork-from outputs/gpu/outputs/all_models_seed2026/training/residual_hrl/best.pt
```

分支 B（`low_only_frozen_high`）：

```
python scripts/train_main_comparison.py \
  --config outputs/stage1_forks_seed2026/configs/low_only_frozen_high.yaml \
  --fork-from outputs/gpu/outputs/all_models_seed2026/training/residual_hrl/best.pt
```

两分支各 1728 episode（864 场景 × 2 个完整覆盖轮），与正式实验剩余的 1728 episode 完全一致；
场景顺序同为 `epoch_permutation_seed_2026`。

### 6.3 预算与计算量

| | 分支 A `high_only_eft` | 分支 B `low_only_frozen_high` |
| --- | ---: | ---: |
| episode / 环境决策预算 | 1728 | 1728 |
| 覆盖轮数 | 2 | 2 |
| 高层 PPO 采样 episode | 1728 | 0（冻结策略激活 1728） |
| 低层 PPO 采样 episode | 0（固定 EFT 1728） | 1728 |
| **optimizer 更新次数** | high 1728 / low 0 | high 0 / low 1728 |

**场景覆盖相同 ≠ 计算量相同。** 两分支更新的参数量、前向反向次数与 optimizer 状态都不同，
`budget.json`、`summary.json` 与 `train_log.csv`（`*_optimizer_updates`）记录实际次数，
报告里只能说「训练场景覆盖匹配」，不能写成等算力。

### 6.4 三种初始化必须区分

| 说法 | 本阶段是否支持 | 依据 |
| --- | --- | --- |
| 从零训练 | 支持 | 不带 `--fork-from` 的普通运行 |
| 从 checkpoint 初始化的新实验 | **支持，也是分叉实验的定位** | 恢复 model + optimizer；RNG、场景排列游标、coverage 计数从 seed 重新开始；scheduler 按 `fork.scheduler_restore` 明确处理 |
| 精确断点续训 | **不支持，且不宣称** | 当前 checkpoint 不含完整 RNG、采样器游标与历史日志状态；checkpoint 的 `training_state.exact_resume_supported` 恒为 `false`，`phase_plan.json` 中同样写明 |

分叉实验的 optimizer / scheduler 处理方式写进 `fork_source.json`（含来源 checkpoint 路径与 sha256、
来源 `global_step`、来源 `best_validation_ratio`、来源 `training_state`、
`initialization: checkpoint_initialization_not_exact_resume`）与每个 checkpoint 的 `training_state`，
不隐式继承来源实验的状态。

   训练 / 保存 / 加载 / 评估：`optimizer_updates={'high': 8, 'low': 4}`，与阶段预算一致。
9. 分叉路径（`--fork-from`）实测可用：`global_step` 从来源续接（8 → 9,10），
   冻结层 `high_loss=null`、`high_optimizer_updates=0`、`scheduler_steps['high']=0`，
   低层正常更新。
10. 正式主模型 step-864 checkpoint 的只读诊断结果（第 5 节表格）。
11. 第一轮分叉点确认为 `best.pt`（step 864）：其 high actor 已训练、low actor 输出层仍全零；
    `latest.pt` 是 step 2592 的最终联合训练模型，权重与 `best.pt` 不同（已逐张量比对）。
12. 分叉配置与正式 checkpoint 的兼容性已实测：model、scheduling environment（`ready_semantics`/
    `insertion_scheduling` 取默认值归一化后）、reward、seed 全部一致；来源 sha256
    `best.pt = db0aef70a80943d5b0ffd12d7babfbdb71a7e0e1826034e2eb0447970bec6c40`。
13. 启动前预检在真实 checkpoint 上跑通（含 1 个真实 probe episode）：
    分支 A `phase=high_only_eft` → `low_loss=None`；分支 B `phase=low_only_frozen_high` → `high_loss=None`。

### 尚待实验验证的假设（不能写成结论）

1. **低层采样是后期退化的主因。** 第 5 节的 +0.1669 差距支持这一方向，但只有 6 个样例，
   必须用 108 场景全量、更多样例与逐轮 checkpoint 复现后才能确认。
2. 第一轮验证 0.999531 → 第三轮 1.011731 的退化来自低层而非高层。
   现有证据只是单点、小样本的方向性提示。
3. 两个分叉实验哪一个能改善 mean_ratio，目前**没有任何实验数据**，不做任何预测。
4. 高层 actor 缺少实时任务—资源匹配信息（resource features 只进 critic）是性能瓶颈之一。
   这是待检视的假设，需要第一阶段定位结果之后再由第二阶段的可开关特征对照实验来判断。
5. `gamma=1` 下 episode 回报等于负的 makespan ratio 已在日志中用
   `diag_reward_equals_negative_makespan_ratio` 实测确认；这确认的是实现一致性，
   不代表该目标一定最优。
