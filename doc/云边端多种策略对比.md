# 云边端多种策略对比实验

更新日期：2026 年 9 月 17 日

本文定义并说明两种已经落实代码的学习基线。两者均在同一个 DAG 环境中逐步选择任务与资源，使用同一模拟器、奖励、训练划分及固定 108 场景 validation。本文不包含正式训练后的实验成绩；当前已完成模型、训练、评估与接口测试。

## 一 方法范围与命名

| 对比方法 | 代码标识 | 核心区别 |
| --- | --- | --- |
| DualGraph PPO | `graph_ppo` | 一个 Actor 对所有合法任务资源动作对建模 |
| Heterogeneous Graph MAPPO 项目适配版 | `tier_mappo` | Device Edge Cloud 三个 Actor 分别提出动作，由学习型协调器选择一个执行 |

原始方案中的论文线索包括 Multi-agent reinforcement learning with graph representation for green edge–cloud computation offloa，以及 Task Placement and Resource Allocation for Edge Machine Learning A GNN-based Multi-Agent Reinforcem。原文只给出了不完整标题和设计思路，因此本实现不宣称逐项复现这些论文，也不宣称复现未提供的原项目源代码。

MAPPO 在这里特指带中央团队 Critic 的协同 PPO 适配：三个 Actor 参数独立，但共享任务图与资源图编码器，并且执行时仍有中央协调器。它不是三个完全独立训练的模型，也不是严格的无协调器分散执行。

## 二 共同环境与数据协议

两种方法固定使用：

- 场景来源：本地 GrapheonRL STG JSON 数据。
- 任务规模：50、100、300。
- 划分：`data/manifests/grapheonrl_mixed_iid_seed7.json`。
- 训练集：432 个基础 DAG，共 864 个场景。
- 验证集：54 个基础 DAG，共 108 个场景。
- test：不训练、不评估；只在加载时核查固定划分数量和基础 DAG 隔离。
- 同一 DAG 的同构和异构实现保持在同一划分。
- 使用数据集原始资源实现，不额外生成更有利的资源。
- 环境提供 ready-task 掩码、永久可行节点掩码及其组合的合法动作对。
- 使用相同的归一化任务、资源、通信、EST 和 EFT 特征。

两种学习基线都不使用 portfolio、LNS、beam、HEFT residual 或 HEFT 兜底。环境仍提供 HEFT 相关特征和 HEFT 归一化尺度，且二者完全一致；“纯策略”指不拼接搜索结果，不意味着完全不使用启发式特征。

训练采用环境默认奖励：新增 partial makespan 的负增量，除以该场景的 HEFT makespan。默认 gamma 为 1，因此整局奖励总和等于负的最终 makespan ratio。没有另加能源、成本或通信惩罚目标。

由于没有安全兜底，两个方法都允许出现 ratio 大于 1；这属于需要如实报告的模型表现，而不是应当隐藏的失败样本。

## 三 方法一 Heterogeneous Graph MAPPO

### 图编码与代理划分

Task GNN 编码全局任务图，Resource GNN 编码资源网络。拓扑与初始特征的图编码在每个 rollout 内缓存；动态任务状态、节点忙时以及任务资源对特征每一步更新。

三个 Actor 的资源范围为：

| Agent | 项目 node_type | 候选动作范围 |
| --- | --- | --- |
| Device | `end` | 当前 ready task 与 end 节点的合法动作对 |
| Edge | `edge` | 当前 ready task 与 edge 节点的合法动作对 |
| Cloud | `cloud` | 当前 ready task 与 cloud 节点的合法动作对 |

Actor 使用全局任务表示、该候选资源的表示、二者交互和动作对特征评分。三个 Actor 使用不同的参数，不直接拿彼此未标定的原始 logits 互相比大小。

### 候选动作与协调器

训练时，每个当前有合法动作的 Agent，从自己的 masked categorical 分布中采样一个候选动作。协调器根据全局任务池化特征及各层级的本地资源池化特征生成投标分数：投标网络输入经过 LayerNorm，输出经过 tanh，被约束到共同的有限区间，再除以固定 temperature。

当前实现的投标取决于状态，而不额外依赖已采样候选动作。这使候选分布与协调器分布的概率定义明确，训练和推理都可以精确重算。

```text
Device Actor → proposal_device
Edge Actor   → proposal_edge
Cloud Actor  → proposal_cloud

Coordinator → 从当前可用层级中选择 tier
最终执行     → proposal_tier 对应的 task_id 和 resource_id
```

验证时，各 Actor 取各自合法动作概率最大者，协调器取投标概率最大的可用层级。此规则对应“先提案、再协调”，并非对全部联合动作概率直接取一个全局最大值。

缺失层级或该层级没有可行节点时，该 Agent 标为 inactive。其内部占位动作不执行、不参与 Actor 或熵损失；协调器不能选中它。同构资源全部映射到 cloud 时，只有 Cloud Agent 有效，这是合法的退化情形。

### PPO 概率与团队价值

每步保存三个候选动作和协调器选择，一共四个策略头的动作、旧 log probability、active mask、共享价值、奖励和 done。环境仍只执行一个任务资源动作对。

```text
旧概率记录
  log π_device(proposal_device | state)
  log π_edge(proposal_edge | state)
  log π_cloud(proposal_cloud | state)
  log π_coordinator(tier | state)

中央 Critic
  V(global task state, all resource state, progress)

团队优势
  A_t = GAE(reward, V, done)
```

更新时，各有效策略头分别计算自己的 PPO likelihood ratio 和 clipped surrogate，使用同一团队 advantage；有效头的 Actor 与 entropy 项取平均。Critic 的 value loss 每个状态只计算一次。

不能只保存最终动作对的概率，再假装它等于三个提案与协调器的概率。本实现也没有对完整四头 log probability 求和后使用单个 joint clipping ratio，而是使用逐头裁剪的协同 PPO 形式。

共享图编码在更新期间重新计算并参与梯度传播，不能把 rollout 时缓存的无梯度 embedding 当成永久冻结编码器。

## 四 方法二 DualGraph PPO

使用与 MAPPO 相同规格的 Task GNN、Resource GNN 和动态特征融合，但只有一个 Actor，直接为全部合法任务资源动作对评分：

```text
Scenario
  → Task GNN 与 Resource GNN
  → 融合动态状态及 pair features
  → 全局合法动作对 logits
  → masked categorical
  → 训练采样  验证 argmax
  → 环境执行并返回奖励
  → 中央 Critic 与 GAE
  → 单 Actor PPO 更新
```

该方法保留题述“图编码、合法动作对、Actor Critic、GAE、PPO”的主要流程。本轮落实的是 DualGraph 版本，没有另外新增 TaskGNN-only 模式，也没有使用现有蒸馏教师标签。

## 五 默认公平性设置

| 项目 | 两种方法的共同设置 |
| --- | --- |
| 图隐藏维度 | 32 |
| Attention heads | 4 |
| Task 与 Resource 图层数 | 各 1 层 |
| Dropout | 0 |
| 训练 epoch | 3 |
| 每 epoch | 无放回打乱并遍历全部 864 个训练场景 |
| Learning rate | 0.0003 |
| Gamma 与 GAE lambda | 1.0 与 0.95 |
| PPO clip coefficient | 0.2 |
| Entropy coefficient | 0.01 |
| Value coefficient | 0.5 |
| 最大梯度范数 | 0.5 |
| PPO update epochs | 4 |
| Minibatch size | 8 个调度状态 |
| Target KL | 0.03 |
| 模型选择 | 每个 epoch 后完整 108 场景验证，选择最小 mean ratio |
| 训练 seed | 默认 2026，可显式指定其他 seed |
| CPU 线程 | 默认 1 |

每个 epoch 都覆盖全部训练场景，而不是随机采样若干 episode 后声称用完数据。默认 3 个 epoch 即 2592 个完整训练 episode。训练顺序使用独立随机生成器，相同 seed 下两种方法的场景顺序一致。

相同 backbone 宽度不代表参数量完全匹配。在本地真实数据的默认特征维度下，Graph PPO 有 31,518 个参数，Tier MAPPO 有 58,979 个参数。报告记录参数量；不把更多 Actor 带来的模型容量差异隐藏起来。参数量严格匹配实验属于后续单独的消融，当前尚未实现。

Target KL 可能使某个 episode 的 PPO 更新提前结束，所以实际 optimizer step 数不一定相同；比较入口核查的是环境 transition 数和预先设置的训练预算，不宣称梯度更新次数或计算量完全一致。

## 七 运行方法

在项目根目录的 PowerShell 中设置：

```powershell
$env:PYTHONPATH = "$PWD\src"
```

### 默认完整训练

```powershell
python scripts/train_graph_baselines.py --config configs/zenodo_graph_ppo_comparison.yaml
python scripts/train_graph_baselines.py --config configs/zenodo_tier_mappo_comparison.yaml
```

训练输出分别位于：

```text
outputs/graph_baselines/graph_ppo/seed_2026/
outputs/graph_baselines/tier_mappo/seed_2026/
```

如希望先完成一轮全覆盖训练，两种方法都使用 `--epochs 1`，并指定新的输出目录。它仍然遍历全部 864 个训练场景、完整评估 108 个验证场景；它不是抽样 smoke 验证。

```powershell
python scripts/train_graph_baselines.py --config configs/zenodo_graph_ppo_comparison.yaml --epochs 1 --output outputs/graph_baselines_one_epoch/graph_ppo/seed_2026
python scripts/train_graph_baselines.py --config configs/zenodo_tier_mappo_comparison.yaml --epochs 1 --output outputs/graph_baselines_one_epoch/tier_mappo/seed_2026
```

没有自动断点续训选项。Checkpoint 保存模型和 optimizer 状态，但初版命令不声称支持精确恢复随机序列。若目录非空，命令会拒绝覆盖；重跑请显式使用新输出目录。

### 统一比较

默认三轮训练都结束后运行：

```powershell
python scripts/evaluate_graph_baselines.py --checkpoints outputs/graph_baselines/graph_ppo/seed_2026/best.pt outputs/graph_baselines/tier_mappo/seed_2026/best.pt --output outputs/graph_baselines_comparison_seed2026 --device cpu
```

比较命令没有 `--split test` 或 `--limit`。它会重新完整评估 validation，并在同一批场景上评估 HEFT。

命令会拒绝：缺少某个 seed 的其中一种方法、重复的 method 与 seed、未完成训练的 checkpoint、不同的数据协议、变化的 manifest、不同训练超参数或 backbone 设置，以及不相等的训练 transition 总数。

Checkpoint 内保存配置 hash、基于配置及 manifest 内容的协议签名和模型输入维度。协议签名不等于原始压缩包的逐字节校验，因此原始数据仍须遵守不可改写约束。只加载可信的本地 checkpoint；PyTorch checkpoint 不是不可信文件的安全交换格式。

### 多 seed 比较

正式研究建议预先固定多个 seed，例如 2026、2027、2028。分别对两种方法运行 `--seed`，然后把所有成对的 best.pt 一起传给比较命令。资源实现及固定 manifest 不随训练 seed 改变。

不要只保留其中最好的 seed。跨 seed 汇总是各个完整 validation 均值的均值与标准差；单 seed 时标准差为 0，不代表已经证明稳定性。

## 八 输出与统计口径

### 每次训练

- `config.yaml`、`runtime.json`、`split_manifest.json`：实验配置、实际设备和固定划分。
- `train_log.csv`：每个训练场景的 epoch、episode、transition 数、奖励、损失和训练调度比值。
- `validation_epoch_NNN`：每个 epoch 的完整验证结果。
- `validation_history.json`：逐 epoch 的选优记录。
- `best.pt`：按全量 validation mean ratio 选出的模型。
- `latest.pt`：最后一轮模型。
- `validation_best`：重新加载 best.pt 后得到的完整验证结果。

best.pt 的 selected_epoch 可能早于总训练轮数；completed_epochs 和 transitions 表示整个训练工作实际完成的预算，而非该选中模型自身的更新轮数。

### 每个模型的验证报告

保留统一的 summary、per_scene、按任务规模分组、按数据来源分组等报告，并新增：

- `tier_placements.csv`：每个场景实际执行到 end、edge、cloud 的任务数；MAPPO 的未获选提案不计入执行落点。
- `ratio_by_resource_type.csv`：同构与异构资源分别报告。
- 参数量、P95 推理时间、是否使用 HEFT 兜底等说明字段。

推理时间沿用公共 Evaluator，包含策略 reset 与镜像环境的开销，不只计一次神经网络 forward。训练耗时统计采样和 PPO 更新，不包含数据加载与周期性验证时间。

### 两种方法的配对比较

- `comparison.csv`：每个 method 与 seed 的 ratio、合法率、平均与 P95 时间、参数量及选中 epoch。
- `paired_per_scene.csv`：同一场景、同一 seed 的两个 ratio 及其差值。
- `comparison.json`：跨 seed 汇总与逐 seed 配对统计。
- `heft`：本次重新计算的公共 HEFT 参考。

差值定义为 MAPPO ratio 减 Graph PPO ratio，因此负数表示 MAPPO 更好。改善、退化、持平使用 1e-9 容差。

每个 seed 的配对置信区间按基础 DAG 成组 bootstrap，同一 DAG 的两种资源实现一起重采样。跨 seed 累计的胜负数量以 seed 与场景的配对数为单位，不假装它们都是独立 DAG 样本。单模型 summary 中的历史通用区间仍为场景级 bootstrap，应与配对分组区间区分。

同一个 validation 被用于 checkpoint 选择和后续比较，结果属于开发阶段证据，不能称为独立 test 泛化成绩。

### 运行记录与设备故障处理

首次 Graph PPO 使用 `auto` 选择 CUDA，在第 3 个 epoch、完成第 1882 个训练 episode 后遇到 `CUDA error: an illegal memory access was encountered`，该运行未完成，不能作为正式配对比较的输入。原始日志和已完成轮次的 checkpoint 保留在：

- `outputs/graph_baselines/graph_ppo/seed_2026/`
- `outputs/graph_baselines_run_20260917/graph_ppo.stderr.log`
- `outputs/graph_baselines_run_20260917/graph_ppo.stdout.log`

为避免两种方法使用不同训练后端，重新建立统一 CPU 运行；没有拼接 GPU 的前两轮与 CPU 的第三轮，也没有减少训练预算。新运行目录：

- 模型与训练记录：`outputs/graph_baselines_cpu_20260917/`
- 流程状态与日志：`outputs/graph_baselines_run_cpu_20260917/`
- 完成后的正式比较：`outputs/graph_baselines_run_cpu_20260917/comparison/`

运行过程中只能报告训练进度和已完成的完整验证，不把训练单场景 ratio、图表单元测试或未完成模型当作最终成绩。此节记录启动和恢复方案；是否完成以 `pipeline_status.json` 的 `status` 字段为准。

### 一条命令串行执行

以下命令用于新的空目录；当前运行已经启动，不应重复执行到同一目录：

```powershell
$env:PYTHONPATH="$PWD\src"
$env:PYTHONIOENCODING='utf-8'
python scripts/run_graph_baseline_comparison.py `
  --output outputs/graph_baselines_run_cpu_20260917 `
  --training-root outputs/graph_baselines_cpu_20260917 `
  --training-device cpu `
  --evaluation-device cpu
```

流水线顺序为 Graph PPO 训练、Tier MAPPO 训练、重载两个完整 best checkpoint 进行配对验证、生成图表。任一步失败都记录 `failed` 和错误原因，不会把部分输出标记为完成，也不会自动覆盖或恢复未完成的训练。两个训练进程不同时运行，避免相互争抢设备资源。

单独训练命令新增 `--device auto|cpu|cuda`；该值会写入保存的配置。流水线对两个训练任务使用同一个 `--training-device`。
